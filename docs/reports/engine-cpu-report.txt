ENGINE CPU REPORT: perf/engine-cpu (October 2026)
==================================================

Problem
-------
The Supabase match-worker edge function is killed with "CPU Time exceeded"
(HTTP 546) at the end of every simulation since the emergent engine (#705)
and phases of play (#706) shipped, so no match completes. The edge runtime
allows about 2 s of CPU per invocation and runs this engine about 3x slower
than the development laptop. Goal: at least 4.5x faster, local median at
most 0.40 s per full match, without changing any result.

Result
------
Bench: npx tsx scripts/bench-engine.ts (six full matches of real ISL squads,
median of the six), same laptop, before and after runs alternated:

  before (main 3cf93c1):  1746, 1733, 1746 ms   -> median 1746 ms
  after  (this branch):    682,  687,  738 ms   -> median  687 ms

Speed-up 2.5x. TARGET NOT MET: 0.69 s locally is about 2.1 s at the edge,
still over the 2 s CPU limit. This branch alone does not fix the incident.

Correctness
-----------
scripts/engine-fingerprint.ts (written and baselined first, commit 0a1c5be):
15 fixed full matches (the six real squads with their managers' game
models in six pairings; the uniform test fixtures; every style preset;
all four formations; personalities; benches so substitutions happen; all
ablation flags off; three every-tick-frame runs, two of them with the full
trace stream). One SHA-256 per case over the canonical serialisation of
the whole result (score, every event, every frame, both phase timelines,
traces). Baseline: docs/reports/engine-fingerprint-baseline.txt.

- After every step below: all 15 fingerprints identical to the baseline.
- The oracle is sensitive: scaling separation's speed cap by 1 + 1e-10
  changed 14 of the 15 fingerprints.
- cpuEquivalence.test.ts pins the rewritten helpers (offsideLineX,
  separation, seek, arrive, timeToReachXY) to the reference code they
  replaced, bit for bit (Object.is, signed zeros and ties included), and
  checks the bound the intercept pruning relies on.
- No floating-point operation was reordered: every rewrite performs the
  same operations in the same order, or skips work whose result is proved
  unused or provably fails the test it feeds.

Steps (each committed and pushed separately; gain = bench median at the
time, tsx unless noted; single runs carry about +/-5% noise)
--------------------------------------------------------------------------
 1. offsideLineX in one pass (no filter/map/sort; stable-sort tie order
    reproduced; NaN falls back to the sort).            1808 -> 1356 ms
 2. possessionLines: skip rebuilding the key string while the plan object,
    final-third flag and outfield players are the same objects.
                                                         1356 -> 1082 ms
 3. buildContext intercept scan: skip path samples a player provably
    cannot reach (timeToReach >= distance / top speed, 1e-6 s margin), skip
    the scan when the whole path's bounding box is out of reach, read
    samples as numbers (timeToReachXY), marking via a flag array.
                                                         1082 ->  985 ms
 4. separation in scalars (no five Vec2s per team-mate).   985 ->  897 ms
 5. PlayerTable: the five per-tick Map<playerId, T> in the tick context
    became arrays indexed by roster slot.      bundle  880 ->  765 ms
 6. estimatePass: lane travel times (exp, log, two atans) computed once per
    pass option instead of per opponent; lane vector hoisted.
                                               bundle  765 ->  748 ms
 7. No per-call closures in thinkJob / estimatePass (tsx keepNames wraps
    each in __name per call).                               857 ->  768 ms
 8. shapePoint skips the formation anchor for outfielders (always replaced);
    corner orderings cached per side.                       768 ->  713 ms
 9. integratePlayer, arrive and seek in scalars.            713 ->  665 ms

Tried and reverted (no gain): a chunked, acceleration-aware reach bound for
the intercept scan (no measurable change over step 3), and reusing the
predicted ball path across ticks when the ball moved exactly as predicted
(slower: the bookkeeping cost more than the rare hits saved).

What is left, and the options
-----------------------------
The profile is now flat: per-player, per-tick AI (intercept scan, job
velocities, job choice, shape points, carrier decisions) with no single
team-level recomputation left to memoise. Per match (bundle): buildContext
about 150 ms (the intercept scan over 25 ball-path samples for 22 players
is most of it), job velocities about 100 ms, job choice about 60 ms,
carrier decisions about 60 ms, dead-ball set-up about 50 ms, GC about 40 ms.
Reaching 0.40 s with identical results would need a structural rewrite of
those loops (struct-of-arrays player state, no Vec2 allocation in the AI),
a large and risky change.

The faster route to completed matches, with byte-identical results: split
one match across several worker invocations (simulate N minutes, persist
the world state, resume in the next invocation). The engine is
deterministic for a given state, so the stitched match equals the
single-run one, and two or three invocations of a match that costs about
2.1 s of edge CPU in total fit the 2 s limit with room. It needs the world
made serialisable first: the per-player rng streams are closures today
(rng.ts makeRng), so their 32-bit state would have to be exposed, plus the
module-level caches in this branch are validated by object identity and
simply rebuild after a resume. The fingerprint oracle can verify the
stitching exactly.
